## 4. 实施顺序与完成标准

### AT1：落实多门与条件地表所需的最小能力

核对真实调用者后，以两座城镇的正式需求为界：

1. [ShopDefinition](../crates/rfb-content/src/definitions/towns.rs) 目前只有 `entrancePosition`；设施已经有 `additionalEntrancePositions`。商店采用同样的入口枚举方式，覆盖商店查找、投影、交易距离检查、旅店与城镇传送落点，以及内容位置校验。多门共享同一 shop ID、库存和店主，不复制商店实例；主门继续提供默认传送／定位锚点。
2. [tasks.rs](../crates/rfb-core/src/game/tasks.rs) 已能更换单个任务入口，尚不能仅凭现有字段表达整个塔体、共享门和设施可用性。只补本轮需要的按现有任务状态／替代结果选择地表格的表达，由 Rust 统一应用；不建立原版脚本解释器，不新增“Home 已解锁”等可推导存档状态。
3. [town.rs](../crates/rfb-core/src/game/town.rs) 的设施入口检查当前主要按坐标，条件门必须让投影和执行共用同一可用性判定。初建、任务接取／结算／失败、离城再入和保存继续都消费同一个结果。
4. 只更新条件控制的格子，不能每次重新生成整张城镇覆盖已开门、地面物、怪物和探索记录。进入／离开任务图时如源恢复为不可站立底材，延续已有可站立返回点处理并说明适配，不能把玩家封进墙里。

完成标准：一个实际多门商店检查证明从两门交易共用库存；一个条件设施场景证明地形、投影、真实命令和保存状态一致。类型确有变化才生成对应 Schema／绑定。仅本城使用的场景细节随 AT2／AT3 实施；不把所有底座抽象成独立框架或外部审批前置。

## 5. 文件范围、版本与检查

主要内容为 [middle-earth.json](../packs/rfb-demo-original/worlds/middle-earth.json)、两城 `towns/`、`shops/`、`townFacilities/`、必要入口 `terrain/`、[legacy-wilderness-selection.json](../packs/rfb-demo-original/legacy-wilderness-selection.json)、locale 和 NOTICE。优先扩充现有来源记录与 importer；不另建长期维护的平行地图清单。

运行时沿用 [wilderness.rs](../crates/rfb-core/src/game/wilderness.rs) 的地表合成／存取、[town.rs](../crates/rfb-core/src/game/town.rs) 的入口与服务、[tasks.rs](../crates/rfb-core/src/game/tasks.rs) 的任务状态及现有 world 转层。前端只消费投影，实际显示缺口才改对应界面。

每个正式内容批次更新包版本和 lock，按[内容开发](../docs/content-development.md)生成实际变化的类型。开发从新存档开始，不维护旧 23×11 存档的坐标兼容层。地图扩大可能改变首次到访和地表怪物采样的 RNG；按实际观察解释差异，不按内容 hash 变化机械刷新契约。两城不是默认出生城，是否涉及全局初始化须由实际 diff 与检查决定。

按[验证与契约](../docs/testing.md)选择相关来源／内容／核心测试，Rust 改动运行对应 Clippy、格式与 diff；涉及共享类型或 RNG 时扩大到实际受影响契约。AT4 默认不重跑无变化的全部 workspace／前端／Android。遵循[并行协作](../docs/parallel-development.md)，本方向负责地图与必要机制；只有真实并发重叠才交接，不预先等待其他方向审批。

本次仅形成计划：完成来源尺寸、符号／门格、现有内容与调用链核对及文档检查；未修改正式内容／运行时，未执行游戏测试或构建。建议顺序为 **AT1 必要能力 → AT2 阿南巴 → AT3 萨洛斯 → AT4 聚焦验收 → AT5 交付收口**。
