## 目标与完成口径

逐批补齐当前游戏能实际获取、鉴定、使用或装备，并能保存恢复的原版物品。保留已完成的共享生成系统，按缺少的内容、规则、入口和证据拆分工作。
每批区分“定义存在、规则完成、入口可达、实际验收”；只有 JSON 或来源身份不能记作可玩覆盖。无自然分配、占位或特殊用途的源记录也要有明确归类，不能为了数量把它们全部放进掉落池。

本计划覆盖基础物品、固定神器、装置效果、特殊对象及书本依赖。新职业/种族、完整领域施法、任务与设施各自仍由原方向负责；物品侧交付共享定义和效果，实际交叉依赖按[并行协作](parallel-development.md)交接。
未开放身份或系统保留依赖；本轮可玩物品扩充完成不自动把 `runtimeParityComplete` 改为 `true`。

- I1–I5 某组物品确实依赖这些语义时，将必要部分提前随该组实现；其他差异独立推进，不能作为所有内容接入的前置重构。
- 改动数量/合并语义时覆盖生成、落地、拾取、拆分/合并、交易、储存、销毁和发现计数中实际受影响路径，以及保存后的后续行动。不能靠存档默认值或刷新哈希掩盖丢失。

完成标准：逐项关闭有行为证据的表示差异；仍采用改编表示的项目写清边界，全原版完成标记据实保留。

### I7：本轮可玩范围验收

- 改为随机制族交付，不等待 I3–I6 全部结束。汇总新增身份、效果、入口及未关闭依赖，核对正式报告和九构筑审计一致；没有新增影响的旧验证沿用已注明范围的证据。
- 下一次 I7 小批优先验证当前已交付但缺专项桌面证据的两条链：I2 动态装置获取→逐实例鉴定→侦测/鉴定及取消→能量恢复→原生读档继续；创造神器卷轴获取→合法目标/堆叠确认/命名或取消→成品装备/射击→原生读档继续。补 Snotling 蘑菇复用冷却这一特殊消费者，采用明确标注的稀有/等级前置。
- 创造神器卷轴及竞技场 AR3–AR5 当前是核心/界面自动验证，合并提交也明确未新增 standalone。决斗者专项证明其自己的新开局、挑战/战技与保存继续；B6/E8.8 证明当时的共享生成/装备范围，均不能替代新卷轴或新装置的桌面操作证据。
- 对本轮新增的交互和机制族安排 Windows Tauri standalone：新角色 → 真实获取 → 鉴定 → 装备/使用 → 原生保存恢复 → 继续行动。稀有或高等级前置可受控准备，但必须明示，不能冒充自然练级。
- 单纯增加同机制数值内容不要求每件各跑桌面测试；新界面、目标选择、特殊实例等真实风险补对应检查。Android 与全仓构建不自动附带。

完成标准：可玩范围与证据对应，未完成项仍可追踪；不以文件数、构建成功或审计绿灯代替行为结论。

## 执行顺序与验证

合并后不再把 I3–I7 当作串行大阶段：先补当前 I2/神器卷轴的 **I7 增量桌面验收**；开发继续按 **I3 实际地点/职业所需神器小批、I4 当前身份相关特殊武器小批**推进。I2 疯狂卷轴不再等待 364，但须独立完成自身分支。I5 随真实领域/职业接入；I6 只在所选小批需要时提前处理。奥林匹斯神祇清单、箱子/雕像及其他交互族按实际依赖另组，不扩大为一次性全量导入。

每次先复查本工作树及主线已新增的物品 ID，防止与职业奖励或地点神器重复。只在同一状态/文件确实交叉写入时协调，不新增共享文件审批。
内容变化更新正式包版本及 lock，类型变化才生成对应 Schema/协议；按[内容开发](content-development.md)使用现有命令。普通候选池扩充仍可能改变全局 RNG 消费，按实际影响执行[验证与契约](testing.md)，说明差异再刷新必要 fixture。
新增物品触及职业/主题/神器条件时同步来源审计、生成矩阵和只读 CI 检查；通用物品不机械复制九构筑全套测试，仅补实际差异与缺失证据。

I0 的盘点回归覆盖当时身份计数、别名去重、显式跳过旧 P3 及错误身份拒绝。I1 首组、I2 首组和本次合并各自已有注明范围的验证记录；后续继续按机制族推进，I7 每次只补新交付的桌面影响。
