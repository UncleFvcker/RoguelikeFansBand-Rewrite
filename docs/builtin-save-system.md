# 游戏内存档

S1–S6 使用现有原生存档格式与备份机制实现，不建立另一套角色存档格式。

## 数据目录

桌面版使用实际 EXE 所在目录的 `userdata/saves/` 保存角色槽位及三份备份，`userdata/profile/` 保存关联角色身份、馆藏检查点与成绩。复制游戏时需连同整个 `userdata` 一起复制。启动工作目录不影响路径。目录不可写或已有另一进程占用时明确报错，不切换到其他目录。Android 受应用沙箱限制，继续使用应用私有数据目录。

全局偏好仍独立保存。旧 AppData 开发存档不自动导入、不删除。

## 操作

- 游戏菜单「保存」／Ctrl+S：首次自动创建槽位，此后更新当前槽位。
- 「另存为」：输入名称建立新槽位，并成为当前槽位。
- 「读取存档」：在物品栏同等尺寸的列表内读取、恢复、删除；可以返回当前游戏。手动存档与角色恢复点分组显示。
- 标题页「继续游戏」：读取最近的有效手动存档。读取成功后继续保存会更新选中的槽位。
- 「保存并退出」／Ctrl+X：写入成功后退出；失败留在当前游戏并提示原因。
- 存在未保存进度时，读取其他存档或关闭游戏提供保存后继续、不保存、取消。取消不加载目标存档。

玩家存档入口不再要求导入／导出文件。底部保留地牢信息，不重新加入存档面板。

## 一致性与验证

复用校验、三份备份、馆藏所有权、终态恢复和成绩记录。只有写入完成后才切换当前槽位；失败不将当前槽位绑定到未写入的文件。游戏目录的进程锁保护目录内共享数据。

S1–S5 实现和 S6 用例准备结束后统一验证：相关前端用例、原生存储／馆藏／成绩用例、普通 Tauri standalone 构建，以及 `node e2e/global-preferences-standalone.e2e.mjs --native-saves`。桌面脚本使用独立复制的普通 EXE、新角色和正常游戏操作；仅损坏恢复与写入失败场景有明确文件故障注入。报告在 `test-results/native-saves/`。

验证优化发布版时，先在 `web` 执行 `npm run build -- --no-bundle`，再将环境变量 `RFB_STANDALONE_EXE` 设为 `target/release/rfb-tauri.exe` 的绝对路径，执行同一存档脚本；未设置时仍使用普通调试版。

S6 结果（2026-09-15）：前端全量 446 项、原生 34 项通过；实机发现并修复行动后保存按钮未刷新，以及失败提示缺失原因两处问题，保存提示定向 7 项通过。最终 standalone 构建含类型检查通过，桌面五组场景全部通过、无未捕获运行时错误。最后一组确认保存失败后原文件不变且游戏继续运行，随后 Ctrl+X 保存并正常退出。脚本恢复测试前的全局偏好；旧 AppData 角色数据不参与测试。
