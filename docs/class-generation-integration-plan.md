# 新职业的物品生成接入计划

状态：第一批已完成，第二至四批待实施。规划及首批核对日期：2026-09-10；代码基线：`b66a317a6`，工作分支：`codex/realms-items`。
首批仅整理来源/实现依据及生成报告，没有修改游戏规则或 CI，也没有补跑或宣称缺失的行为测试通过。

## 目标与范围

让每次新增职业、开放新领域构筑时，都能发现遗漏的物品生成适用性核对；先补齐当前八个可玩构筑，之后随职业接入维护。
复用现有生成器、职业入口、审计脚本和测试。新增的是开发检查，不是运行时职业注册系统。

完成后应满足：正常创角增加一个构筑，如果没有对应审计记录，检查明确失败并指出 Build/Class ID；
已有职业开放另一领域，也必须审查该构筑的书本、偏好和消费者，不能因为 Class ID 相同而自动放行。
“无专属差异”必须是有来源依据的显式结论；“依赖未实现系统”必须保留缺口。

本批不导入新职业、全部剩余物品、Craft 领域、神器卷轴或重铸，不补全原版堆叠表示，也不安排八职业乘全部种族的笛卡尔积测试。
只有核对中确认的当前可达缺陷才进入生产代码修复。

## 第一批：整理八职业的适用性依据

**交付：可维护的审计输入和逐构筑结论，先不宣称缺失测试已通过。**

1. 从实际创角入口取得 Build，读取正式 `builds`/`classes` 解析 Class、领域和相关装备能力。
2. 核对 `ego.c`、`object2.c`、`artifact.c` 的已有条件清单，以及实际关联的装备模板、装置使用、书本和战斗消费者。
   既要覆盖直接职业判断，也要覆盖通过装备槽、骑乘、领域或技能间接产生的差异；源码搜索结果不能自行证明“无差异”。
3. 复核旧六职业记录，重点补心灵术士和狂战士。每个 Build 按下列范围记录结论，引用共同条件，避免复制规则正文。

| 核对范围 | 必须区分的事实 |
| --- | --- |
| 基础分配与 Tailored/Acquirement | 身体槽位、类别偏好、领域书、累计发现数、成品可用性 |
| Ego 与负向生成 | 专属物化、属性/诅咒、重量和质量限制；没有专属差异时引用通用路径 |
| 随机神器 | 自然/主题/卷轴入口、职业 bias、特性概率、价值限制与实际消费者 |
| 固定神器及奖励 | 已导入且可达的职业分支、明确奖励；缺少内容或入口的分支单列 |
| 使用与保存 | 装备、装置/激活禁用、感知鉴定、实际战斗或属性、实例与后续 RNG 连续性 |

审计输入集中到 `design/generation-build-applicability.json`，将目前脚本内需人工维护的条件记录一并迁入，
不同时维护两套 `conditionScopes`。最低信息为：来源提交、稳定条件 ID、来源位置与适用入口、Build ID、
`implemented` / `no-special-difference` / `deferred` 结论、理由、实现及测试引用、未完成依赖。
职业或领域数据仍从正式包读取；审计输入只描述已审查事实，不参与运行时决策。

**验收：**八个当前 Build 均有记录；旧“狂战士未开放”标签被真实结论替代；
自然和卷轴分支分开；任何未完成项有明确依赖，不能仅靠补一个 `implemented` 字符串关闭。

首批结果见[审计输入](../design/generation-build-applicability.json)：36 条来源条件集中维护，八个真实 Build 各记录五个范围，复用共同来源和实现/测试引用。
狂战士 `artifact.c:1320-1326` 实际为 WARNING 10%／NO_TELE 90%（其他职业反向），旧“心灵感应”说明已纠正；Rust 阈值与来源一致。
心灵术士 Priestly bias 及后续 20% Warrior 转换只属于未开放的卷轴模式，自然/主题调用明确保留区别。
剩余当前可达证据为两个新构筑的生成→消费者→保存及后续 RNG 衔接，以及狂战士 WARNING/NO_TELE 边界与实际消费者；这些进入第三批。
神器卷轴、重铸及缺失的身份敏感固定神器另列 deferred，未因职业开放而自动关闭。

首批已运行完整来源审计（160 Ego、146 装备底材、41 类导入器未映射标志），并检查入口/条件/缺口引用及实现/测试路径和符号。
测试引用只表明可复用证据位置，不表示本批重跑 Rust 或桌面验收。新入口的只读检查、异常输入测试和 CI 接入仍属第二批。

## 第二批：接入自动遗漏检查

**交付：扩展现有 `audit-egos.mjs`，让新增入口遗漏在 CI 中可见。**

保留原有带原版仓库参数的完整审计入口，新增 `--check-applicability` 只读模式：
读取实际创角目录、正式 Build/Class 和审计输入，检查覆盖关系，不启动 Rust importer、不访问原版仓库、不重写报告。
把这项检查放进现有前端 CI job；不新增服务、自动化任务或 CI 专用原版镜像。

检查至少拒绝：

- 可玩 Build 没有审计记录，包括已有 Class 新开放的领域 Build。
- 重复记录、缺失正式 Build/Class、悬空条件 ID、与实际入口矛盾的“身份未开放”理由。
- 已提交生成矩阵中的 Build/Class/适用性结论与当前入口及审计输入不一致，防止只补输入却遗漏报告更新。
- `no-special-difference` 缺少核对理由，或 `implemented` 缺少适用入口、实现/验证引用。
- 仍有当前可达未完成项，却把该构筑或全部可玩构筑标为完成。

合法的未导入内容、未开放系统可以保留 deferred，不能伪称完整对齐。
无记录的新增入口导致检查失败；有记录的缺口与是否允许该职业按明确受限范围开放，仍由职业需求决定，不能由脚本自动豁免或禁止。

完整审计读取原版 Git 对象核对条件并生成现有 `ego-contract-audit.json`。当前可玩范围的完成标记从审计记录推导，
不再无条件写死 `true`；全原版 `runtimeParityComplete` 继续依据剩余范围保留 `false`。
测试路径存在仅证明引用有效，不代表测试已执行；最终测试结果记录在提交说明和相应验收文档。

复用 Node 内置测试，用最小输入覆盖“新增职业漏记”“同职业新 Build 漏记”“无差异缺理由”“deferred 与完成标记冲突”及有效记录。
无需复制八职业静态快照来凑测试数量。

**验收：**本地与 CI 使用同一检查；缺失第九个 Build 时能失败并定位，补足真实审计记录后才通过；检查不产生文件改动。

## 第三批：补缺失的行为回归与实际消费者证据

**交付：八职业的证据与记录一致；只修实际发现的生产缺口。**

优先复用 [分配测试](../crates/rfb-core/src/game/loot/allocation.rs)、
[Acquirement 测试](../crates/rfb-core/src/game/tests/acquirement.rs)、
[生成适用性测试](../crates/rfb-core/src/game/ego/applicability.rs)及随机神器、狂战士和心灵术士的既有测试。
八职业可以共享最小的正式新游戏/生成/保存基础检查；已有等效覆盖的条目不再复制一套。

- 心灵术士：核实职业 bias 的真实触发模式、概率和普通生成是否应受影响；若仅在未开放卷轴入口触发，则保留函数级证据与入口限制。
- 狂战士：核实随机神器 WARNING/NO_TELE 分支、Tailored 成品选择，以及生成物与卷轴/装置/装备激活禁用、强行卸装等已有消费者的关系。
  原版允许生成但角色不能使用的物品，不能为了测试成功而人为从池中删除。
- 无专属差异的职业：使用真实 Build 和既有通用路径证明适用性，不伪造 Class ID 作为可玩证据。
- 概率分支用可复现的边界或固定种子测试验证，并覆盖保存后的实例与后续 RNG；不要求 C/Rust 同种子产物相同。

需要桌面证据时，扩展已有 `--ego`、`--mindcrafter`、`--berserker` 场景，先适配当前创角控件。
只对新职业的代表性可达差异做实际生成物获取、装备/使用或拒绝、保存恢复和继续行动；
低概率物品可从真实新角色导出档准备，保留馆藏绑定并说明前置条件。不能用高阶法师四例替代新职业验证，也不要求每职业重跑全部四例。

如果发现生成规则缺陷，修复放进现有职责模块；内容变化才升 pack/lock，类型变化才生成绑定/Schema。
公共 RNG、初始化或共享状态确实改变时执行相应完整契约检查，逐项解释差异，不预定刷新 fixture。

**验收：**记录中的每项当前可达差异都有有效消费者证据；缺少入口的分支不冒充桌面验收；相关检查通过后才更新完成结论。

## 第四批：写入日常接入流程并交付

**交付：下一次职业接入能发现并执行这项工作。**

在[内容开发](content-development.md)的职业/领域接入流程中加入本计划入口和检查命令；
在[并行协作](parallel-development.md)明确：新增职业的一方负责对应 Build 的来源核对、审计记录和专属消费者证据，
物品方向负责必要的共享生成器修改，集成方负责检查目录与记录没有脱节。共享文件本身不成为审批点，只有实际交叉写入才交接。

交付时更新生成矩阵及[状态页](status.md)，区分入口覆盖、规则实现、实际检查与剩余依赖。
将“新增职业/新领域 Build → 来源核对 → 记录差异或无差异 → 完成实现与证据 → CI 检查”的要求带入后续职业计划，
不持续给本文件追加各职业流水账。

**最终完成标准：**当前八职业没有未分类的生成适用性；新增入口漏记会失败；生成记录与真实入口一致；
专属差异具有适当验证；未导入内容、未开放系统和原版对象表示限制继续单列。

## 验证范围与执行顺序

按第一至四批顺序实施，各批可独立提交；第一批发现的问题在第三批闭合，不能在第二批为了检查通过删除失败条件。
第一、二批仅修改审计/开发工具时运行 Node 检查与完整来源审计，不触发整轮游戏构建。
第三批按实际变化运行相关 Rust/前端测试；桌面使用 Tauri standalone，测试存档从新角色开始。
不因普通合并重跑全量 workspace、全部前端或 Android；若发现公共规则变化，则按[验证与契约](testing.md)扩大检查。

各批只记录实际执行的检查；首批完成不代表第二至四批或八构筑行为验收完成。
