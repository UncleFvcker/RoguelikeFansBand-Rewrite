# 并行协作

## 三个工作树，四个对话

这是当前已经启动的工作方式，不是创建新任务的要求。先检查 `git worktree list` 与各树状态，复用现有目录。

| 对话 | 工作树 | 分支与责任 |
| --- | --- | --- |
| 种族职业 | `D:/codex/RoguelikeFansBand-Rewrite` | `main`；直接开发、测试并提交本方向 |
| 主线集成 | 同上 | `main`；日常只读审查，接管后合并、修复冲突、验证与推送 |
| 法术道具 | `D:/codex/RoguelikeFansBand-Rewrite-realms-items` | `codex/realms-items`；领域、书本、物品、Ego、神器、装置 |
| 地牢城镇 | `D:/codex/RoguelikeFansBand-Rewrite-dungeons-towns` | `codex/dungeons-towns`；地点、设施、任务、生态、专属怪物/守卫 |

旧 `monsters-next`、`items-next`、`class-next` 分支已退役。不要因历史交接中的路径恢复它们。若工作树名单仍有不存在目录的登记，它不是可继续工作的分支；清理登记不属于日常功能任务。

## main 的写入交接

集成的 merge、生成文件、冲突修复和提交都会改变文件、索引与 HEAD。两个对话不能因为“集成不开发功能”就同时写同一个目录。

日常由种族职业写入。需要集成时：

1. 种族职业完成当前小批次的必要检查与独立提交，交出提交号并暂停写入。
2. 集成确认没有未保存的功能修改，再合并和验证。无关未跟踪文件如 `release/` 原样保留，不要求清空整个目录。
3. 集成提交、推送并报告新的 HEAD；种族职业重新读取状态和实际相关 diff 后继续。

没有交接时，集成可以审查已提交内容，但不自动 stash、提交其他人的修改或开始合并。集成期间种族职业不启动会修改同一构建目录或生成文件的检查。两个独立工作树仍可并行推进。

## 文件与内容的归属

归属按行为/稳定 ID 判断，不把每个共享目录设成审批关卡：

- 种族职业负责自身的 Class/Race、成长、出生、专属能力和新职业 Build。
- 法术道具负责领域书本、通用物品与效果；已有职业的新领域 Build 随领域接入。新职业同时依赖新领域时，明确该 Build 的单一负责人。
- 地牢城镇负责世界与地点定义、设施/任务、生态与守卫；奖励、库存和出生物引用同一物品定义，不复制近似物品。
- 法术召唤与地牢生态共享已有 actor。没有独立的全怪物导入方向，新增必要怪物随实际调用它的工作安排。
- Fluent、图集、协议和核心共用文件按本批所需接入。只有实际并发重叠或未满足依赖才协调。

两方确实需要同一项新机制时，由一个方向先交付可验证的底座，其他方向同步后使用。仅服务本批的必要改动直接随本批提交，不强制切成多个等待阶段。

## 职业与领域生成审计的交接

新增职业或开放新领域 Build 时，采用[内容开发的生成接入闭环](content-development.md#职业与领域-build-的生成接入)。后续职业/领域计划须包含来源核对、逐 Build 记录、实际消费者证据和 CI 检查，不能等到集成时才补审计。

| 责任方 | 本批交付 |
| --- | --- |
| 新增 Build 的一方 | 新职业由种族职业方向负责，已有职业的新领域由领域接入方负责；维护对应 Build 的来源依据、[审计输入](../design/generation-build-applicability.json)、专属生成/使用/保存证据及更新后的报告。跨方向的新职业/新领域 Build 沿用单一负责人。 |
| 法术道具方向 | 负责实际需要的共享生成器修改与共同规则回归，沿用现有模块和条件记录；把受影响入口、验证结果和剩余依赖交给 Build 负责人。没有共享规则变化时，不增加等待本方向审批的步骤。 |
| 集成方向 | 涉及 Build、生成规则或审计记录的合并，核对最终创角目录、正式 Build/Class、审计输入和生成矩阵；运行 `node scripts/audit-egos.mjs --check-applicability`。报告过期时先合并真实依据，再按内容开发指南重生成报告并复查。 |

交接说明沿用提交号和实际结果，补充相关 Build ID、条件 ID、已完成证据及仍开放的 gap 即可。共享审计文件本身不是审批点；只有两方确实重叠写入或存在未满足依赖时才协调写入顺序。
不得通过删除失败条件、清空未完成 gap 或选择某一侧旧报告来解决合并冲突。检查通过不代替行为验收；验证仍按实际影响选择，不因这项交接扩大为整轮构建或全量测试。

## 提交、同步与集成

每批交付简要说明：提交号、目标行为、稳定 ID/共享文件、版本或 RNG/状态影响、验证结果和剩余问题。未变的协议/存档等合并成一句，无需填写无关检查清单。

两个独立分支在自己的修改已妥善保存后，用普通 merge 同步最新 main；不改写已被依赖的历史，不强推。集成按冻结的交付提交处理依赖和冲突。种族职业的提交已经在 main，无需再次 cherry-pick。

集成时把内容定义正确合并后再确定 pack 版本与 hash；不要选某一侧 lock 直接了事。生成物由最终定义生成。验证范围取实际交叉影响，不因普通合并运行全部历史测试；规则见[验证与契约](testing.md)。

本机三个工作树通过各自未入库的 `.cargo/config.toml`，将 `[build] build-dir` 设为 `D:/codex/RoguelikeFansBand-Rewrite/target`，共用 main 的 Rust 中间构建缓存。另设 `rustc-workspace-wrapper = ".cargo/workspace-rustc.cmd"`，各树的同名脚本仅执行 `@echo off` 和 `%*`，原样转交编译命令。Cargo 将解析后的包装器路径计入工作区 crate 的文件名哈希，因此自身代码按工作树隔离，第三方依赖仍共用。不能只设置共享 `build-dir`：实测不同版本的工作区 crate 会被错误判为 Fresh。

Cargo 1.96 已验证支持；最终产物的 `target-dir` 保持各树默认目录，前端依赖、`dist` 和 E2E 产物也保留各树目录。两个本机配置文件由共享 Git `info/exclude` 排除，不提交到仓库。创建新工作树时需单独配置；不要把包装器改为三个工作树共用的同一绝对路径。

相同版本、特性和编译参数的依赖可复用；工作树路径、代码或内容变化仍可能触发重编译，并行 Cargo 构建可能等待共享缓存锁。`cargo clean` 会影响共享中间缓存，清理前应确认其他方向没有构建或测试正在使用它；不要手工删除其他工作树的输出。旧独立缓存暂时保留，后续按需清理。

## 已启动对话如何采用新文档

此次整理把日常指南迁到 `docs/`。旧入口如 `design/class-race-import-handoff.md` 和 `design/parallel-development-handoff-20260909.md` 留有迁移链接。档案可只读查证，但不继续向旧批次日志追加当前状态。

给正在运行的对话发送：

```text
继续当前任务，保留正在做的修改。项目文档已重新整理：
请读取当前根目录 AGENTS.md，以及 docs/ 中与本任务相关的指南。
旧 design 文档和 docs/archive 只作历史资料，不继承其中的旧待办、固定测试矩阵或审批步骤。
复用现有实现与测试；只补当前缺失行为，相关检查通过就交付，真实状态和并发边界仍保留。
涉及新增职业或领域 Build 时，将 docs/content-development.md 的生成接入闭环纳入当前计划和验收，按 docs/parallel-development.md 交接审计责任。
本工作树尚未同步新文档时，先按这条消息执行；不要为同步文档强行 merge、stash 或重开任务。
用几行说明本批最小实现和验证范围，然后继续推进。
```

集成在正常同步时带入文档调整。若分支仍修改了旧交接文件，合并时保留其中的新事实到当前状态/相应指南，必要的历史证据进档案；不要把旧日志整段恢复为当前规则。
