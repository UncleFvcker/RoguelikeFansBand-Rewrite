## 第三步：按缺失的共同机制交付神器

### 目标与基线

本节对应五步策略中的第三步：**同一批神器需要同一个尚缺的机制时，随首件补最小实现，首件通过真实行为验证后再展开同组余项。**它不等于下文旧余量队列中的“第三项身份敏感内容”，也不要求先完成所有神器激活。

本次重排基线为`codex/realms-items@091ef5160`；重新核对的RFB `master`仍为`a0d92b6378d148c5262cc236b8fa6ed2ca06a54c`，实现时须再次记录实际来源。全部source ID与参数以[逐项清单](../design/remaining-item-coverage-review.json)为唯一名册。**C1–C3完成原注明范围；C4a–C4c及C5a–C5b完成普通入口与当前身份下的核心验收。**这五个小批是原C4／C5的拆分，不增加第二套覆盖计数。

可直接复用的合并成果：祖尔十四种龙鳞甲与普通／Ego／随机神器生成路径；`player_stats`、`movement`、`turn`和`wall_passage`测试中的种族／状态穿墙规则；`progression`的永久属性损失、当前／最大经验与资源重算；牧师、战法师的领域改换和物品消费者。当前创角共102个Build，后续适用性审计必须沿现有完整集合，不再沿用C3时的70构筑快照。

### C0：逐组核对，先排除已有能力

每组开始时只追该组的 `a_info`、底材、`ART_*` 引用、通用 flag 和激活调用链，并与当前工作树及相关方向的已提交实现对照。核对结果记录到现有逐项清单的来源／依赖字段，不增设一个独立调度系统。缺口分为三种：

- **仅内容／参数缺口：**底材、执行器和实际入口都存在，回第一步接入；同名 token 缺少 importer 分支不自动证明运行时缺能力。
- **共同规则缺口：**进入 C1–C5 中对应组。首件必须连同定义和获取／使用／保存一起交付，不能只提交没有调用者的底座。
- **独有规则或身份／地点缺口：**按下文交接表转第四／第五步，或继续原 B8–B10；缺口未解决的 ID 保持开放，不删 flag、不用普通掉落替代专属奖励。

已核实的复用起点：`ItemUseEffectDefinition` 已有 `Sequence`、`AbilityEffect`、`Escape`、`RechargeFromDevice`、`RidingCharge`；`AbilityEffectDefinition` 已有 `RandomChoice`；光速状态及速度消费者、基本球／线／锥形投射、恢复、魅惑和召回均有实现。`loot.rs` 已保留随机神器的底材激活，Ego／随机神器也不是空白系统。

因此 **84／128 的 ESCAPE、46／141 的装置间充能、324 的 CHARGE、279 的 LIGHT_SPEED** 先核对既有路径，不能各建一套机制。特别是 importer 的 `RECHARGE_FROM_DEVICE` 当前会生成 `recharge-from-player`，而运行时已有真正 `RechargeFromDevice`：固定神器须接对入口，并审查该映射的既有随机神器／装置调用者，不能以 token 已支持认定语义正确。修改共享映射时验证源／目标装置选择、能量转移、取消和保存，不顺便改另一种充能规则。

### 每批实施、验证与关闭

1. **确认交接和来源。**先检查本工作树修改及相关已提交代码；每批记RFB实际来源提交。C4已具备合并后的龙鳞甲前置，复用Z2／Z6现有证据；后续只在真实交叉依赖时协调其他方向。
2. **首件贯通。**内容进入现有导入／正式包路径；规则进入 `game/item_use`、`game/abilities`、`game/player_combat`、`game/player_stats` 或现有 `loot` 职责。Rust `Game`统一决定RNG、状态和ID；前端只消费必要目标／状态投影。优先复用现有定义，确有表达缺口才增一个最小字段／变体。
3. **首件先验证，再扩同组。**新角色走至少一个正式获取入口，完成拾取、未知保存、鉴定、装备、真实行为、冷却／状态中保存和续演。首件失败就修当前共享路径，不先铺满同组内容。后续件复用共同覆盖，只补源差异与入口证据；不逐件复制相同矩阵。
4. **同步派生产物。**内容改变更新pack版本／lock、来源选择、逐项映射、分配与适用性审计、受影响的源C估值；仅类型变化才生成Schema／协议绑定。状态哈希输入变化才审State Hash Schema，纯内容变化不以contentHash为由刷fixture。
5. **按实际影响检查。**每个小批先跑新行为与直接旧调用者，内容变化核名称／来源／lock及受影响估值／审计，类型变化检查生成Schema或协议；公共状态／RNG／投影影响按范围执行active契约。C4a重点普通／Ego／随机神器激活，C4b重点共享状态与投射，C4c重点穿墙／保存，C5重点永久属性／经验／诅咒与随机激活；不预设测试数量或机械全workspace。若新增读取、双装置选择等交互，补对应前端及Tauri standalone桌面路径；既有Zul桌面证据不代替新神器流程，自然练级与Android不自动纳入。
6. **独立提交与记录。**分别报告定义、规则、入口、核心／桌面证据及剩余依赖；详细完成记录留提交说明，计划只更新状态。A/B阶段曾约定末尾统一验证，**不自动沿用到C阶段**；默认每组通过检查再交付。

构建照常使用Cargo命令，沿[共享缓存约定](parallel-development.md#提交同步与集成)复用main中间缓存；各树的workspace wrapper和最终产物目录保持隔离，不另设`CARGO_TARGET_DIR`绕开配置。并行时允许等待缓存锁，不为解锁执行`cargo clean`。

第三步关闭以共同机制和该组可独立交付的成员均有证据为准，同时对剩余ID留下具体归属；不要求剩余258项归零，也不把有条件成员的机制复用标成整件完成。实际验证范围见上文与状态页。

## 每批关闭条件

- **内容定义：**完整源参数、权威中文名、底材和来源记录；正式包版本与 lock 更新。仅类型变化才生成 Schema／协议，不手改生成物。
- **规则与入口：**逐件检查 flags/pval、诅咒、随机附加、激活和专属消费者；至少一个符合源规则的真实获取路径。普通池／instant／专属奖励分别取证；受控稀有度和等级前置须明示。
- **保存与唯一性：**从新角色出发，验证生成、拾取、未知状态／鉴定、装备或使用、保存后继续；覆盖本批实际随机或冷却边界。不以直接物化代替普通生成，也不为每件复制一套相同测试。
- **检查范围：**运行直接受影响的既有测试、内容与名称／来源校验、lock 和生成审计；公共 RNG 或状态输入变化再按实际范围执行全局契约。纯内容变化不自动刷新 fixture，不因普通合并重跑全 workspace。
- **交付口径：**分别报告定义、规则、入口和验收；专属桌面证据留在 I7，明确未执行的部分。需要交付可玩桌面产物时使用 Tauri standalone；既有构建或核心受控测试不替代桌面流程。

每批结束只更新当前映射、待办和长期依赖，具体完成细节放提交说明，不继续向本计划追加批次流水账。
